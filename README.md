# 제주 데이터 관제실 — 관광·교통 이상 신호 탐지·원인 설명 AI Agent

> 「제주 AI·빅데이터 활용 AI Agent 개발 챌린지」 제출작 · 팀 숨비소리

제주데이터허브의 **유동인구·와이파이·버스** 일 단위 데이터를 43개 읍면동별로 지켜보다가,
평소와 다른 날(이상 신호)을 찾아 **기상·공휴일·입도객·다른 신호의 동반 변화**와 대조해 원인 후보를 설명합니다.

- **이 PC 안에서만 동작**: 화면은 `127.0.0.1`에서만 열리고, 판단 모델(tev1)도 로컬(Ollama)에서 돕니다. 데이터가 외부 LLM으로 나가지 않고 API 비용이 없습니다.
- **숫자를 지어내지 않음**: 답변·브리핑의 모든 숫자에는 근거 결과 id(`[R1]`)가 붙고, 검증기가 계산 결과와 대조해 통과한 문장만 보여 줍니다.
- **원인은 '후보'로**: 원인 판정은 근거와 확률(확신도 상·중·하)로 제시하며 인과를 단정하지 않습니다.

## 화면 (탭 4개)
| 탭 | 하는 일 |
|---|---|
| 관제판 | 읍면동 × 날짜 점수 히트맵, 이상 구간 목록(하루짜리 **일시 급변** / 3일 이상 **지속 변화**) |
| 상세 분석·브리핑 | 실제 값 vs 기대값 그래프, 같은 날 맥락, 다른 신호·제주 전체 동반 변화, tev1 원인 판정(확률), 검증된 브리핑과 HTML 저장 |
| 질문하기 | "이호동 2024년 7월 28일에 왜 사람이 많았어?"처럼 묻기(연도를 빼면 데이터 기간 안의 가장 최근 해) → 질문 분류(tev1) → 정해진 도구 실행 → 검증된 답변 |
| 데이터 품질 | 신호별 마지막 날짜, 위치 매핑 결과(매칭 실패 건수 포함) |

## 구조
```
허브 Open API ──► app/ingest  (데이터별 일일 쿼터 관리, 멈춘 페이지부터 이어받기)
                    │  data/cache/*.parquet
                    ▼
               app/store    (정류소·AP → 43개 읍면동 매핑, 신호별 날짜×읍면동 표)
                    ▼
               app/analytics (탐지: 같은 요일 중앙값 / STL 잔차 → 이상 구간, 맥락·동반 변화)
                    ▼
 질문 ─► app/agent/local ─► 도구 6종(app/agent/tools) ─► app/llm/judge (tev1 원인 판정, 실패 시 규칙)
            (tev1 질문 분류)        │                       │
                                    ▼                       ▼
                         app/report (템플릿 문장) ─► app/agent/verify (숫자·날짜·근거 검증) ─► 화면(app/ui)
                         app/rag (데이터 명세·API 문서·반출 기준 검색, BM25)
```
도구 6종: `get_series`, `detect_anomalies`, `scan_regions`, `find_co_movements`, `check_context`, `search_docs`

## 빠른 시작 (Windows)
자세한 설치는 [docs/설치_실행_매뉴얼.md](docs/설치_실행_매뉴얼.md)를 보세요(비전공자용 단계별 안내).
```powershell
py -3.12 -m venv .venv
.venv\Scripts\pip install -r requirements.txt
# Ollama 설치(https://ollama.com/download) 후
ollama pull tev1:4b
```

브라우저에서 `http://127.0.0.1:8501`을 엽니다. Ollama가 없어도 실행되며, 이때 원인 판정·질문 분류는 규칙 기반으로 자동 대체됩니다.

## 평가 (재현: `python -m eval.<이름>`)
| 평가 | 방법 | 결과(2026-11-11, 분석 기간 수집 완료 데이터) |
|---|---|---|
| 탐지 (`inject_eval`) | 신호별 실제 시계열에 가짜 이상(±20/40/80%, 1일·4일) 480회 주입 | 기본값(같은 요일 중앙값, 점수 3.5)의 이상일 재현율: 유동인구 54.7%(평소 경보 100일당 2.8일), 와이파이 23.1%, 버스 31.8%. 같은 경보 빈도에서 STL 잔차는 +2.1%p·+5.5%p·−0.9%p로 차이가 작아, 설명하기 쉬운 같은 요일 중앙값을 기본으로 둠 |
| 검증기 (`verify_eval`) | 실제 브리핑 60개에 오류 주입 | 정상 통과 100%. 검출: 숫자 변경 94.3%, 근거 바꿔치기 92.3%(13건 중 12), 근거 삭제·지어낸 숫자·근거 없는 원인 단정 100% |
| 질문 분류 (`intent_probe`) | 설계에 쓰지 않은 질문 12개 | tev1:4b 83%, tev1:0.8b 58%, 키워드 규칙 33% |
| 판정 모델 (`tev1_probe`) | 정답을 정한 원인 판정 10건 | tev1:4b 10/10 |
| 문서 검색 (`rag_probe`) | 답이 있는 문서를 정해 둔 질문 16개 | 상위 3개 안 적중: 설계 질문 9/10, 따로 둔 질문 6/6 |
| 실제 사례 (`real_cases`) | 실제 데이터 질문 7개 | 모두 검증 통과, 정답 확인 가능한 2건(추석·이호테우축제) 판정 일치 |
| 처리 시간 (`speed_probe`) | 실제 데이터로 질문 6종 × 2회, 질문 → 검증된 답변까지 | 센터 PC와 같은 6코어로 묶은 CPU(개발 PC, 센터 실측 아님): 원인 질문 중앙값 13.7초, 지역 훑기 4.8초, 문서·범위 밖 질문 4~5초. GPU 0.6초 이하, 모델 서버 없음(규칙 기반) 2.5초 이하 |

과정과 해석은 `notebooks/01~05`에 실행 결과와 함께 기록되어 있습니다. 문제 정의·구조·실행 결과·검증·한계·센터 활용 방안은 `docs/결과_설명서.md`(PDF: `docs/결과_설명서.pdf`, `python docs/_build/build_results.py`로 생성)에 정리했습니다.

## 한계
- 원인 판정은 상관에 기반한 **후보**이며 인과가 아닙니다. 근거가 없으면 '판단 불가'로 답합니다.
- 유동인구(583·589)는 2024-04~2026-08을 분석하지만, 기상(579)·축제(761)는 2025-03, 입도객(580)은 2025-07까지만 있습니다. 그 뒤 날짜는 해당 근거를 '확인 불가'로 표시합니다(없다는 뜻이 아님).
- 외국인 유동인구(589)는 2025-04·05 두 달이 허브 원천 오류(값 범위 초과로 API 500)라 빠져 있습니다.
- 축제(761)는 장소 항목이 없어 행사명에 지명이 명시된 단기 행사만 연결합니다(분석 기간 161건 중 9건). 나머지 행사는 원인 근거에서 빠집니다.
- 검증기는 숫자·날짜·근거 id를 확인하지만, 지명이나 표현의 정확성까지 보장하지는 않습니다. 예: 공휴일 이름을 쓴 문장에 같은 날짜가 든 다른 결과를 달면 통과합니다(평가에서 놓친 1건).
- 와이파이 신호는 날마다 변동이 커서 같은 기준에서 재현율이 낮습니다(23%). ±80% 변화는 이상일의 43~65%를 잡지만 ±20~40% 변화는 거의 잡지 못합니다.
- 외부 LLM 연동은 현재 버전에 포함하지 않았습니다(도구 호출 루프 `app/agent/loop.py`는 공급자 무관 인터페이스로 준비).
